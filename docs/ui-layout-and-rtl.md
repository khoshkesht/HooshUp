# مرجع طراحی رابط موبایل، چیدمان و RTL

این سند مرجع واحد طراحی و اصلاح UI پروژه است. مبنای آن فایل پیشنهادی کاربر `GODOT_MOBILE_UI_RULES.md` و قواعد اختصاصی قبلی پروژه است؛ در تعارض طراحی، قواعد فایل جدید مقدم‌اند. متن فایل ورودی، مرجع بررسی و ادغام است و به‌تنهایی دستور اجرای مهاجرت یا نصب روی گوشی محسوب نمی‌شود.

هدف، یکسان‌بودن رفتار چیدمان، جهت متن و لمس در اجرای Godot و APK است. نمایش پس‌زمینه می‌تواند با نسبت تصویر تغییر کند، اما جای منطقی، خوانایی و دسترس‌پذیری کنترل‌ها باید ثابت بماند. تأیید در ادیتور یا headless به‌تنهایی تأیید Android نیست.

## شرط الزام‌آور مهاجرت: حفظ کامل ظاهر موجود

طبق دستور صریح کاربر، مهاجرت فقط تغییر روش چیدمان است و هیچ بازطراحی گرافیکی مجاز نیست. تمام منوها، تولبار، تنظیمات، پنل پیشرفت، نشان‌ها، دیالوگ‌ها و سایر اجزای موجود باید گرافیک فعلی خود را حفظ کنند: تصاویر، قاب‌ها، آیکون‌ها، رنگ‌ها، شفافیت، سبک دکمه‌ها، نسبت دارایی‌ها و ترکیب بصری داخلی.

- جایگزین‌کردن قاب یا دکمهٔ گرافیکی با پنل ساده، StyleBox یا ظاهر جدید ممنوع است. Theme مشترک نباید سبک فعلی را بازنویسی کند.
- فقط مالکیت لایه‌ها، Anchor، Container، SafeArea، تبدیل مختصات، محدودیت اندازه و هم‌ترازی ناحیهٔ لمس اصلاح می‌شوند. اندازه و محل کل قاب برای نمایشگرهای مختلف می‌تواند با حفظ نسبت تصویر و ترکیب داخلی تنظیم شود.
- کنترل متصل به یک بخش از قاب هنری، در مختصات نسبی همان قاب چیده شود؛ تصویر و ناحیهٔ لمس همیشه یک هندسه داشته باشند. قواعد Container به معنی حذف قاب هنری نیستند.
- جابه‌جایی گروه‌های HUD طبق مرجع فقط با حفظ گرافیک اجزای موجود انجام شود؛ تغییر محتوای تصویر یا ساخت تصویر جایگزین نیازمند درخواست جداگانهٔ کاربر است.
- رفع نقص چیدمان، مانند عنوان خارج صفحه یا کنترل غیرقابل لمس، مجاز است؛ تغییر سلیقه‌ای ظاهر مجاز نیست.
- تأیید هر مرحله شامل مقایسهٔ تصویر قبل و بعد است. مرحله‌ای که ظاهر موجود را عوض کرده باشد، حتی با پاس‌شدن آزمون هندسه، کامل محسوب نمی‌شود.

این شرط بر پیشنهادهای عمومی استفاده از Theme، PanelContainer یا بازسازی UI در تمام مراحل مهاجرت مقدم است.

## ۱. تصمیم‌های ادغام و قواعد مقدم

| موضوع | قاعدهٔ قبلی | قاعدهٔ مرجع جدید |
| --- | --- | --- |
| بوم طراحی UI | `1280×720` | `1920×1080`، افقی و نسبت مرجع ۱۶:۹ |
| Stretch Aspect | `keep` و قاب مرکزی ۱۶:۹ | `expand` و استفاده از فضای واقعی قابل‌استفاده |
| محل عناصر UI | مختصات ثابت روی بوم و `contain_scale` دستی | Anchor برای اتصال به لبه/مرکز؛ Container برای چیدمان گروه |
| ناحیهٔ امن | مستطیل مرکزی هم‌نسبت با بوم | ناحیهٔ امن واقعی دستگاه، تبدیل به مختصات UI، به‌علاوهٔ Margin |
| محل منو و راهنما | تولبار و منو در بالا-چپ | منو و راهنما در بالا-راست؛ آواتار در سمت چپ |
| لایهٔ UI | برخی رابط‌ها همراه صحنه/تصویر | HUD و Overlay در CanvasLayer مستقل از حرکت و زوم محیط |
| فارسی | جداسازی LTR چیدمان از RTL متن | همین جداسازی حفظ می‌شود؛ مختصات با زبان سیستم آینه نمی‌شوند |
| آزمون | بوم مرجع و گوشی | ماتریس نسبت تصویر، زبان، وضعیت پنل و لمس، سپس APK همان نسخه |

در بند ۱۲ فایل ورودی، مثال `Layout Direction = RTL` برای متن با اصل «RTL فقط برای متن» همان فایل ناسازگار است. در این مرجع، جهت متن با `text_direction` تعیین می‌شود؛ `layout_direction` والدهای چیدمان و کنترل‌های دارای Anchor، LTR است. این اصلاح فنی مانع بازگشت مشکل جابه‌جایی چپ/راست در Android می‌شود.

## ۲. تنظیم پروژه و واحدهای طراحی

تنظیم هدف در `SourceProject/project.godot`:

```ini
[display]

window/size/viewport_width=1920
window/size/viewport_height=1080
window/stretch/mode="canvas_items"
window/stretch/aspect="expand"
```

- جهت انتشار بازی Landscape است؛ تنظیم پروژه و خروجی Android باید سازگار باشند.
- `1920×1080` اندازهٔ طراحی است، نه ابعاد ثابت Root UI یا فرض دربارهٔ رزولوشن گوشی.
- اندازهٔ واقعی Parent در زمان اجرا مبنای چیدمان است. در `expand`، بوم منطقی در جهت لازم بزرگ‌تر می‌شود و نسبت تصویر حفظ می‌شود. [مستند چندرزولوشنی Godot](https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html#stretch-settings)
- مقادیر UI در واحد منطقی بوم هستند؛ پیکسل فیزیکی صفحه، مختصات تصویر و مختصات محلی Control قابل‌جایگزینی با یکدیگر نیستند.
- Stretch موتور مسئول مقیاس کلی است. اعمال مجدد `scale` یا `contain_scale` روی Root/HUD برای جبران رزولوشن ممنوع است؛ نتیجه می‌تواند مقیاس دوگانه و لمس نامنطبق باشد.
- اندازهٔ پنجرهٔ تست دسکتاپ از اندازهٔ بوم طراحی مستقل است. برای آزمون چند اندازه، پنجرهٔ تست باید قابل‌تغییر اندازه باشد.

## ۳. جداسازی محیط، پس‌زمینه و رابط

| نوع عنصر | ساختار | مبنای چیدمان |
| --- | --- | --- |
| محیط، کاراکتر، شیء و سرنخ متصل به محیط | `Node2D` و تبدیل محیط | مختصات محلی World و حرکت/زوم آن |
| HUD، منو، تنظیمات، فرم انتخاب مأموریت و مینی‌گیم | `Control` زیر CanvasLayer | Parent، Anchor، Container و ناحیهٔ امن |
| پس‌زمینهٔ تزئینی تمام‌صفحه | `TextureRect` | پوشاندن صفحه با حفظ نسبت تصویر |
| دیالوگ، تأیید، پنل تلفن و پنجرهٔ سفارشی | `Control` در OverlayLayer | ناحیهٔ امن، لبه یا مرکز |

استفاده از Node2D برای چیدمان HUD/Menu/Popup جدید ممنوع است. کنترل UI نباید فرزند تصویر متحرک، World زوم‌شده یا Camera2D باشد. داده‌های محتوا، دارایی‌ها و منطق بازی از قواعد چیدمان جدا می‌مانند. متن و دکمهٔ قابل‌تعامل داخل تصویر پس‌زمینه قرار نمی‌گیرند.

ساختار مرجع:

```text
Main
├── World (Node2D)
│   ├── Background
│   ├── SceneObjects
│   └── Hotspots
├── HUDLayer (CanvasLayer, layer = 10)
│   └── RootHUD (Control, Full Rect, LTR)
│       └── SafeArea (Control)
│           └── SafeMargin (MarginContainer, Full Rect)
│               ├── TopHUD (HBoxContainer)
│               │   ├── AvatarAndProgress
│               │   ├── Spacer (Control, Expand)
│               │   └── MenuAndHint
│               └── MissionUI
└── OverlayLayer (CanvasLayer, layer = 20)
    └── OverlayRoot (Control, Full Rect, LTR)
        ├── ModalShade (Full Rect)
        └── SafeArea
            └── SafeMargin
                └── Dialog / Menu / Settings / PhoneOverlay
```

RootHUD و OverlayRoot کل Viewport را می‌پوشانند؛ SafeArea فقط بخش قابل‌استفاده را. Root UI نباید `size = Vector2(1920, 1080)` یا ابعاد ثابت دیگری داشته باشد. اتصال به دوربین و دنبال‌کردن تبدیل World برای CanvasLayer رابط غیرفعال است. شمارهٔ Layer ترتیب مستقل رسم را تعیین می‌کند. [مستند CanvasLayer](https://docs.godotengine.org/en/stable/tutorials/2d/canvas_layers.html)

## ۴. Anchor، Offset و Container

- Root و لایه‌های پوشاننده: `Control.PRESET_FULL_RECT`، Anchorهای `0, 0, 1, 1` و Offsetهای صفر.
- عنصر بالا-راست: هر دو Anchor افقی `1` و هر دو Anchor عمودی `0`.
- عنصر بالا-چپ: هر دو Anchor افقی و عمودی `0`.
- عنصر پایین-راست: هر دو Anchor افقی و عمودی `1`.
- پنل مرکزی: CenterContainer داخل ناحیهٔ امن؛ یا هر چهار Anchor برابر `0.5` با اندازهٔ محدود به فضای Parent.
- مقدار Offset فاصله از Anchor را تعریف می‌کند؛ عدد ثابت برای محل مطلق صفحه ممنوع است.
- برای گروه عناصر از MarginContainer، HBoxContainer، VBoxContainer، GridContainer، PanelContainer و AspectRatioContainer استفاده شود.
- Spacer با `SIZE_EXPAND_FILL` فضای آزاد را جذب کند. اندازهٔ متن و کنترل با Size Flags و `custom_minimum_size` مدیریت شود.
- Container مالک چیدمان فرزندان مستقیم خود است؛ تغییر دستی `position`، `size`، Anchor یا `scale` آن فرزندان برای مقابله با Container ممنوع است. [راهنمای Containerهای Godot](https://docs.godotengine.org/en/stable/tutorials/ui/gui_containers.html)
- پنل‌های دارای محتوای بلند از ScrollContainer استفاده کنند. حداقل اندازهٔ پنل بیرونی نباید از کوچک‌ترین فضای امن پشتیبانی‌شده بزرگ‌تر باشد.
- افزایش تعداد گزینه‌ها یا طول متن باید باعث بازچینی، Wrap یا Scroll شود؛ کوچک‌کردن متن تا حد ناخوانا یا بریدن گزینهٔ مهم پذیرفته نیست.

نمونهٔ دکمهٔ بالا-راست زیر یک Control معمولی، نه زیر Container:

```gdscript
var button := Button.new()
button.layout_direction = Control.LAYOUT_DIRECTION_LTR
button.text_direction = Control.TEXT_DIRECTION_RTL
button.alignment = HORIZONTAL_ALIGNMENT_RIGHT
button.text = "منو"
safe_parent.add_child(button)
button.set_anchors_and_offsets_preset(Control.PRESET_TOP_RIGHT)
button.offset_left = -104
button.offset_right = -32
button.offset_top = 24
button.offset_bottom = 96
button.custom_minimum_size = Vector2(72, 72)
```

این نمونه اندازهٔ اسمی `72×72` و فاصله از لبه را تعیین می‌کند و به عرض ثابت صفحه وابسته نیست. تنظیم Layout پس از `add_child()` انجام می‌شود تا Parent واقعی مشخص باشد. برای UI قدیمی نیز جهت LTR پیش از اتصال و چیدمان پس از اتصال تثبیت شود؛ تعیین دوبارهٔ Position ثابت، راه‌حل نهایی مهاجرت نیست.

مقادیر ثابت مجاز: Margin، Padding، Gap، اندازهٔ آیکون، حداقل اندازهٔ کنترل، ضخامت حاشیه، شعاع گوشه و اندازهٔ فونت در Theme. نمونه‌های ممنوع: `position.x = 1700`، `global_position` وابسته به صفحه یا `Vector2(1650, 70)` برای HUD. انیمیشن با جابه‌جایی نسبی یا Fade مجاز است، اما وضعیت نهایی باید به چیدمان Parent بازگردد.

## ۵. LTR فیزیکی و RTL متن

- Rootهای UI، SafeArea، Containerها و کنترل‌های دارای Anchor صریحاً `Control.LAYOUT_DIRECTION_LTR` باشند.
- متن فارسی با `Control.TEXT_DIRECTION_RTL` و راست‌چین نمایش داده شود. برای Label از `horizontal_alignment` و برای Button/OptionButton از `alignment` استفاده شود.
- جهت چیدمان از زبان سیستم یا Locale ارث‌بری نشود. فارسی‌بودن سیستم نباید ترتیب آواتار، منو یا مختصات لمس را عوض کند.
- هرگز ثابت عددی جهت چیدمان را hard-code نکنید؛ از نام ثابت‌های Godot استفاده کنید.
- اگر یک گروه معنایی باید از راست به چپ خوانده شود، ترتیب فرزندان آن را در ساخت Container تعریف کنید؛ RTL والد ابزار جابه‌جایی فیزیکی نیست.
- متن ترکیبی فارسی، عدد و شناسهٔ فنی باید جداگانه از نظر نمایش بررسی شود. نام نمایشی محصول فقط «هوش آپ» است.
- `text_direction` و `layout_direction` دو ویژگی مستقل Control هستند. [مرجع Control](https://docs.godotengine.org/en/stable/classes/class_control.html)

## ۶. ناحیهٔ امن واقعی گوشی

ناحیهٔ امن باید بریدگی دوربین، گوشه‌های گرد و ناحیه‌های اشغال‌شده توسط رابط سیستم را لحاظ کند. قاب مرکزی ۱۶:۹، Safe Area دستگاه نیست.

قرارداد سرویس مشترک SafeArea:

1. در Android ناحیهٔ قابل‌استفاده را از `DisplayServer.get_display_safe_area()` بخواند. این API روی Android و iOS پیاده‌سازی شده است. [مرجع DisplayServer](https://docs.godotengine.org/en/stable/classes/class_displayserver.html#class-displayserver-method-get-display-safe-area)
2. مستطیل نمایشگر را به فضای محلی Root UI تبدیل کند؛ پیکسل نمایشگر مستقیماً Offset/Position کنترل نیست.
3. تبدیل باید موقعیت پنجره و Stretch را لحاظ کند. برای Root در پنجرهٔ اصلی، تبدیل معکوس `get_screen_transform()` مبنای تبدیل صفحه به مختصات محلی است؛ تبدیل برای پنجرهٔ Embedded/SubViewport باید متناسب با همان میزبان انتخاب شود. [مرجع تبدیل CanvasItem](https://docs.godotengine.org/en/stable/classes/class_canvasitem.html#class-canvasitem-method-get-screen-transform)
4. نتیجه را با مستطیل Root تقاطع دهد، سپس SafeArea را تنظیم کند. SafeMargin داخل آن Padding طراحی را اعمال کند.
5. در نبود نتیجهٔ معتبر، محدودهٔ پنجره با Margin محافظه‌کارانه مبنای fallback باشد؛ این وضعیت در لاگ تشخیصی مشخص شود.
6. با Resize، تغییر جهت/Insets و بازگشت برنامه به Foreground، محاسبه را تازه کند. نوار ناوبری و حالت Immersive/Edge-to-edge با تنظیم APK آزموده شوند.
7. برای ورودی متن، صفحه‌کلید نرم نیز جداگانه مدیریت شود تا فیلد فعال و دکمهٔ تأیید قابل‌دسترسی بمانند.

Padding پایه در واحد منطقی: چپ/راست `32` و بالا/پایین `24`؛ بسته به پنل در بازهٔ پیشنهادی فایل جدید، چپ/راست `24–40` و بالا/پایین `20–40` تنظیم شود. Padding داخل ناحیهٔ امن اعمال می‌شود؛ Insets دستگاه و Margin دستی نباید دو بار یک نوار سیستم را کم کنند.

این سرویس تنها مرجع SafeArea برای HUD و Overlay است. محاسبهٔ پراکنده در هر پنل یا وابستگی به IP/مدل یک گوشی ممنوع است.

## ۷. پس‌زمینه و محتوای وابسته به تصویر

برای پس‌زمینهٔ تزئینی تمام‌صفحه:

```text
Layout = Full Rect
Expand Mode = Ignore Size
Stretch Mode = Keep Aspect Covered
Mouse Filter = Ignore
```

- تصویر با حفظ نسبت، صفحه را می‌پوشاند؛ Crop محدود برای هنر پس‌زمینه مجاز است.
- UI، متن مهم و نقاط تعامل ضروری نباید همراه تصویر Crop شوند.
- عکس یا تصویر محتوایی که دیدن کل آن لازم است، `Keep Aspect Centered` یا AspectRatioContainer بگیرد.
- نقطهٔ تعامل متصل به میز/تلفن/شیء محیط، جزو World است؛ تصویر، نشانگر و ناحیهٔ لمس آن باید یک تبدیل مشترک داشته باشند.
- Crop یا Pan محیط نباید دسترسی به یک سرنخ اجباری را از بین ببرد؛ مسیر Pan/Zoom یا قاب مناسب لازم است.
- قاب هنری لپ‌تاپ، تلفن یا دفتر می‌تواند نسبت ثابت داشته باشد، اما متن و دکمه‌های روی آن Control مستقل و قابل‌چیدمان‌اند. مختصات نرمال‌شده یا Anchor نسبت به خود قاب مجاز است؛ مختصات مطلق صفحه مجاز نیست.
- هیچ HUD یا Overlay از `cover_scale` محیط یا زوم تصویر برای تعیین جای خود استفاده نمی‌کند.

## ۸. پنل‌ها، گزینه‌ها و ترتیب لایه‌ها

| لایه | مقدار هدف | محتوا |
| --- | ---: | --- |
| World | Canvas معمولی `0` | محیط و سرنخ‌ها |
| HUDLayer | `10` | آواتار، پیشرفت، منو، راهنما، شمارش‌معکوس |
| OverlayLayer | `20` | منو، تنظیمات، انتخاب مأموریت، دیالوگ و تأیید |
| DiagnosticsLayer، فقط Debug | `30` | برچسب و قاب تشخیصی بدون دریافت لمس |

این شماره‌ها قرارداد هدف‌اند؛ همهٔ اجزا از تعریف مشترک استفاده کنند. در یک Canvas، ترتیب فرزندان و z-index محلی هنوز باید روشن باشد؛ z-index یک Canvas نمی‌تواند جایگزین Layer مستقل شود.

- پنل سفارشی و سایهٔ Modal در Overlay ساخته شوند. سایه تمام صفحه را بپوشاند و محتوای پنل داخل ناحیهٔ امن باشد.
- وسط پنل نسبت به SafeArea تعیین شود، نه نسبت به مرکز تصویر World.
- OptionButton و PopupMenu داخلی آن از نظر اندازه، جای بازشدن، جهت متن، Theme و لمس در APK آزموده شوند. پنجرهٔ داخلی استاندارد موتور با کنترل سفارشی داخل تصویر جایگزین نشود.
- محتوای طولانی Popup اسکرول‌پذیر باشد؛ آخرین گزینه هم قابل‌انتخاب بماند.
- کنترل مخفی یا غیرفعال نباید لمس World یا پنل دیگری را مسدود کند.
- تا پایان Modal، دریافت ورودی World و کنترل‌های پشت آن متوقف شود؛ صرف رسم سایه کافی نیست.

## ۹. نمایش، لمس و زمان محاسبهٔ Layout

- کنترل‌های تعاملی و سایهٔ Modal: `MOUSE_FILTER_STOP`؛ تصویر و برچسب تزئینی روی دکمه: `MOUSE_FILTER_IGNORE`. Root شفاف HUD معمولاً Ignore است تا بخش خالی صفحه را مسدود نکند.
- z-index به‌تنهایی اولویت دریافت ورودی Control را تعیین نمی‌کند؛ ترتیب رابط، پوشاننده‌ها، Mouse Filter و مسدودشدن World بررسی شوند. [مرجع ورودی Control](https://docs.godotengine.org/en/stable/classes/class_control.html#class-control-method-gui-input)
- ناحیهٔ لمس باید با شکل نمایش‌داده‌شده و اندازهٔ قابل‌استفاده روی گوشی منطبق باشد؛ کوچک‌بودن آیکون دلیل کوچک‌کردن سطح لمس نیست.
- پس از ساخت درخت و پایان مرتب‌سازی Containerها، هندسه اندازه‌گیری شود. اندازهٔ صفر در اولین `_ready()` نباید به‌عنوان مقدار نهایی ذخیره شود.
- محاسبه‌های ضروری Layout به تغییر اندازه و ناحیهٔ امن واکنش نشان دهند؛ یک `call_deferred()` جایگزین رسیدگی به Resize نیست.
- حرکت بازشدن پنل باید فرزند بصری یا مقدار نسبی را انیمیت کند و Anchor/Container را خراب نکند.
- در تطبیق مختصات، Control و Parent را در فضای یکسان مقایسه کنید. `get_global_rect()` لزوماً مستطیل پیکسلی اسکرین‌شات نیست.
- مثبت‌بودن `position.x` معیار کافی نیست؛ معیار، قرارگرفتن کنترل قابل‌تعامل در محدودهٔ امن و نبود Clip/هم‌پوشانی ناخواسته است.

## ۱۰. فونت، Theme و ثبات بین دسکتاپ و APK

- فونت فارسی به‌صورت دارایی پروژه و در خروجی Android موجود باشد؛ برای متن اصلی به fallback فونت سیستم اتکا نشود.
- Theme مشترک اندازهٔ فونت، آیکون، Padding، حداقل اندازه و StyleBox کنترل‌ها را تعیین کند؛ Override محلی فقط با دلیل مشخص.
- Theme و جهت متن OptionButton/PopupMenu، حالت‌های عادی، Hover، Pressed، Disabled و Focus بررسی شوند.
- متن بلند با Wrap و رشد Container مدیریت شود؛ متن حیاتی Clip نشود. تست با بلندترین عنوان مرحله/مأموریت و نام بازیکن انجام شود.
- تغییر DPI/مقیاس نمایش دستگاه نباید با یک ضریب دستی مستقل در هر پنل جبران شود.
- Godot اجراکننده و Export Template باید نسخهٔ سازگار داشته باشند. Renderer، Orientation و تنظیم Immersive/Edge-to-edge هنگام مقایسه ثابت و ثبت‌شده باشند.
- تفاوت عمدی ابزارهای Debug و Release ثبت شود؛ رابط اصلی و مسیر تعامل کاربر نباید فقط در `OS.is_debug_build()` ساخته شوند.

## ۱۱. قراردادهای اختصاصی بازی

این قواعد محتوایی حفظ می‌شوند؛ اجرای هندسهٔ آن‌ها تابع بخش‌های قبل است.

### تولبار، منو و راهنما

- `components/game_toolbar.tscn` کامپوننت مشترک HUD با شفافیت `0.85` است؛ آواتار و پیشرفت سمت چپ و گروه منو/راهنما سمت راست قرار می‌گیرند.
- در تنظیمات، منوی باز و پنل پیشرفت مرحله، تولبار مخفی است. مپ اصلی به‌جای تولبار، دکمهٔ `assets/pics/ui/menu.png` را در بالا-راست ناحیهٔ امن دارد.
- شمارهٔ مرحله، امتیاز و وضعیت پنج مأموریت روی همین تولبار هستند؛ جز استثنای مپ، دکمهٔ مستقل دیگری برای منو/راهنما ساخته نشود.
- مأموریت تکمیل‌شده با `assets/pics/ui/star.png` و مأموریت تکمیل‌نشده با قفل نمایش داده می‌شود.
- پیش از Hint، تأیید جریمهٔ ۵ امتیازی لازم است. متن Hint از `data/mission_hints.json` و دارایی آن `bubble2.png` است.
- در امتیاز ناکافی، به‌جای تأیید هزینه/Hint، پیام «امتیاز کافی نداری؛ فعلاً نمی‌تونی این راهنما را ببینی.» با یک دکمهٔ تأیید نمایش داده شود. هنگام تأیید هزینه، موجودی دوباره بررسی شود.
- پنل تأیید در مرکز SafeArea قرار می‌گیرد؛ اندازهٔ آن تابع محتوای Container و فضای موجود است، نه یک مستطیل ثابت روی صفحه.

### نمای چت لپ‌تاپ و مینی‌گیم

- همهٔ پیام‌های چت با افکت تایپ، RTL و راست‌چین‌اند. پیش از پیام هوش آپ، `...` با مکث `1.5` ثانیه نمایش داده شود، مگر دادهٔ مأموریت زمان دیگری تعریف کند.
- پرسش، پاسخ و بازخورد هوش آپ در باکس پاسخ چت می‌مانند؛ داخل باکس ورودی یا روی دکمهٔ انتخاب قرار نمی‌گیرند.
- «مینی‌گیم روی صفحه» لایهٔ مستقل UI و «مینی‌گیم روی چت» داخل قاب چت است. انتخاب نوع به سناریو وابسته است.
- عنوان، سؤال، انتخاب‌ها و بازخورد با Container در فضای امن چیده می‌شوند؛ زوم پس‌زمینه جای مینی‌گیم را تعیین نمی‌کند.
- رنگ دکمه‌ها: پایه `#3badae`، Hover `#54c3c1`، حاشیه `#8bd8d2` و تکمیل‌شده `#6fae9c`.

### بابل فکر و شمارش‌معکوس

- `presentation: "thought"` از بابل فکر استفاده می‌کند؛ Flip فقط افقی است. بابل Hint/صحبت با بازیکن Flip افقی و عمودی دارد و کوتاه‌تر است.
- هر دو بابل با شفافیت `0.85` در سمت راست ناحیهٔ امن و زیر تولبار Anchor می‌شوند. ارتفاع تابع نسبت دارایی و محتواست؛ `y=140` و ارتفاع‌های ثابت بوم قبلی معیار جدید چیدمان نیستند.
- نسبت بصری ارتفاع‌های قدیمی `136.8` برای فکر و `129.96` برای Hint در مهاجرت هنری حفظ شود؛ این اعداد مختص دارایی قدیمی‌اند و موقعیت صفحه را تعیین نمی‌کنند.
- شمارش‌معکوس فقط از `components/countdown.tscn` استفاده می‌کند؛ عدد فارسی روی `assets/pics/ui/countdown.png` و محل پیش‌فرض، پایین-راست پنل با Anchor است.
- زمان و رفتار پایان شمارش را مصرف‌کننده تعیین می‌کند.

### هات‌اسپات‌های محیط

در کد قدیمی، پس‌زمینه `z=-20`، سایه `-10` و نشانگر سرنخ `-5` است. این ترتیب محلی برای محیط حفظ می‌شود؛ رابط در Layer بالاتر قرار می‌گیرد. هات‌اسپات‌های قدیمی `top_level` باید همراه تبدیل تصویر و ناحیهٔ لمس مهاجرت شوند؛ تبدیل بخشی از آن‌ها بدون بخش دیگر ممنوع است.

## ۱۲. وضعیت فعلی و مسیر مهاجرت

تنظیم جاری پروژه اکنون `1920×1080/expand` است. گزارش اجرای مرحله‌های ۴ و ۵ با حفظ قاب‌های گرافیکی و نتیجهٔ بررسی دسکتاپ در [گزارش مهاجرت هنری](mobile-ui-art-migration.md) آمده است. ترکیب یکپارچهٔ تولبار فعلی طبق دستور حفظ ظاهر باقی می‌ماند؛ پیشنهاد جای‌گذاری گروه‌ها مجوز بریدن یا بازطراحی تصویر نیست.

فهرست صحنه‌ها، لایه‌ها، وابستگی‌های چیدمان و شواهد مرحلهٔ اول در [گزارش وضعیت پیش از مهاجرت](mobile-ui-baseline.md) ثبت شده است. این گزارش مبنای مقایسهٔ تغییرهای بعدی است.

زیرساخت مشترک و انتخاب‌گر تستی در مرحله‌های ۲ و ۳ پیاده‌سازی شدند؛ معماری، نتیجهٔ آزمون و موارد باقی‌مانده در [گزارش اجرای مهاجرت](mobile-ui-implementation.md) آمده است.

در زمان تدوین این مرجع، `project.godot` هنوز `1280×720` و `keep` دارد؛ `ResponsiveLayout.DESIGN_SIZE` نیز `1280×720` است. `ResponsiveLayout.safe_rect()` فقط قاب متناسب با طراحی را محاسبه می‌کند. رابط‌های قدیمی هنوز چیدمان و Scale دستی دارند؛ پنل تستی اکنون از زیرساخت جدید استفاده می‌کند. موارد قدیمی تأیید انطباق با مرجع جدید محسوب نمی‌شوند.

این ویرایش سند، تنظیمات اجرایی پروژه را مهاجرت نمی‌دهد. تغییر عدد رزولوشن به‌تنهایی کافی نیست و می‌تواند رابط قدیمی را کوچک یا جابه‌جا کند. ترتیب مهاجرت:

1. کنترل‌ها را به World، HUD، Overlay و محتوای متصل به قاب تصویر دسته‌بندی کنید؛ ابتدا سرویس مشترک SafeArea و Rootهای Full Rect را آماده کنید.
2. برای HUD و پنل‌ها، Positionهای ثابت را به Anchor/Container تبدیل کنید؛ فرم انتخاب مرحله/مأموریت از نخستین موارد بررسی است.
3. داده‌های World و نقاط هنری قدیمی `1280×720` را در فضای محلی خود نگه دارید و یک تبدیل مشخص برای نمایش داشته باشید؛ استفادهٔ آن‌ها به‌عنوان مختصات UI ممنوع است.
4. مهاجرت Theme، اندازه‌های اسمی، تنظیم `1920×1080` و `expand` و حذف Scale اضافی را هماهنگ انجام دهید. نسبت `1.5` فقط راهنمای انتقال اندازه‌های هنری از بوم قبلی است، نه راه‌حل جای‌گذاری کنترل.
5. محاسبهٔ قاب هنری را از SafeArea واقعی جدا کنید؛ helper قدیمی با نام «safe» نباید به‌جای سرویس امن دستگاه استفاده شود.
6. هر پنل مهاجرت‌شده را با معیارهای زیر تأیید کنید؛ تا پایان مهاجرت، موارد باقی‌مانده را در گزارش همان تغییر مشخص کنید.

دستورات جست‌وجوی محدود برای ممیزی:

```powershell
rg -n 'position\s*=|global_position|set_position\(|position\.[xy]\s*=' SourceProject/components SourceProject/scripts
rg -n 'contain_scale|cover_scale|design_to_safe|safe_rect|top_level' SourceProject/components SourceProject/scripts
```

وجود این الگوها به‌تنهایی خطا نیست؛ وابستگی به مختصات صفحه در HUD/Overlay باید بررسی شود. مختصات World و جابه‌جایی انیمیشن نسبی از چیدمان ثابت صفحه تفکیک شوند.

## ۱۳. آزمون اجباری و شواهد تأیید

| رزولوشن فیزیکی تست | نسبت | هدف |
| --- | --- | --- |
| `1920×1080` | ۱۶:۹ | مرجع طراحی |
| `2400×1080` | ۲۰:۹ | گوشی عریض |
| `2280×1080` | ۱۹:۹ | گوشی عریض دیگر |
| `1920×1200` | ۱۶:۱۰ | تبلت |
| `2340×1080`، در صورت امکان | ۱۹٫۵:۹ | پوشش تکمیلی |

این اندازه‌ها، اندازهٔ پنجره/خروجی تست‌اند، نه ابعاد ثابت Root UI.

- روی همهٔ نسبت‌های اجباری، پنل بسته/باز، Popup گزینه‌ها، بلندترین متن، Scroll و تغییر اندازه بررسی شوند.
- اجرای معمولی دسکتاپ با زبان سیستم فارسی و انگلیسی، یا شبیه‌سازی Locale هر دو، باید محل فیزیکی یکسانی داشته باشد.
- در اجرای Embedded ادیتور، حالت `Stretch to Fit` برای تطبیق Viewport با پنجره انتخاب شود؛ نمای ادیتور جای اجرای واقعی صحنه را نمی‌گیرد. [راهنمای آزمون Stretch](https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html#stretch-settings)
- شبیه‌سازی بریدگی و Insets در تست دسکتاپ انجام شود؛ بررسی واقعی ناحیهٔ امن و لمس در APK نیز لازم است.
- برای مقایسه، APK همان نسخهٔ کد، داده، دارایی و تنظیمات باشد. شناسهٔ Build/نسخه و Debug/Release ثبت شود تا APK قدیمی با خروجی جدید اشتباه نشود.
- پس از هر تغییر GDScript، اعتبارسنجی headless اجرا و خطاها بررسی شوند؛ این آزمون نمایش، فونت، SafeArea یا لمس Android را تأیید نمی‌کند.
- وقتی کاربر نصب توسط عامل را ممنوع کرده است، بررسی APK روی دستگاه به کاربر واگذار می‌شود؛ آزمون باقی‌مانده باید در گزارش مشخص شود.
- اگر آزمون دستگاه انجام نشده، گزارش باید صریحاً «تأیید روی گوشی انجام نشده» بگوید؛ اختلاف با APK حل‌شده اعلام نشود.

شروط پذیرش هر UI:

- [ ] Rootها Full Rect و چیدمان فیزیکی LTR هستند؛ متن فارسی RTL و راست‌چین است.
- [ ] HUD/Overlay به عرض ثابت، زوم World یا Scale دستی دوباره وابسته نیستند.
- [ ] کنترل قابل‌تعامل در ناحیهٔ امن است؛ متن مهم، آیکون و سطح لمس Crop نشده‌اند.
- [ ] هیچ خروج ناخواسته از Parent یا هم‌پوشانی کنترل‌ها وجود ندارد. محتوای داخلی ScrollContainer می‌تواند بزرگ‌تر باشد، مشروط به Clip و دسترسی با Scroll؛ عناصر موقت خارج صفحه در انیمیشن نباید قابل‌لمس باشند.
- [ ] جهت فیزیکی منو/راهنما و آواتار با تغییر Locale عوض نمی‌شود.
- [ ] Popup، آخرین گزینه، دکمهٔ تأیید و صفحه‌کلید نرم قابل‌استفاده‌اند.
- [ ] لمس روی گوشی با تصویر منطبق است و پشت Modal منتقل نمی‌شود.
- [ ] همهٔ نسبت‌های اجباری بررسی و وضعیت تست دستگاه ثبت شده است.
- [ ] اگر GDScript تغییر کرده، اعتبارسنجی headless انجام شده است.

## ۱۴. تشخیص اختلاف Godot و APK

وقتی یک کنترل در APK دیده نمی‌شود، پیش از افزودن Offset جدید این موارد بررسی شوند: نسخهٔ APK، Debug/Release، ساخته‌شدن Node، `visible` و `is_visible_in_tree()`، اندازه و جهت Parent، Anchor/Offset، حداقل اندازه، Scale، Theme/فونت، Clip، Layer و پوشاننده‌های ورودی.

لاگ Debug برای Root، پنل و کنترل مشکل‌دار باید اندازهٔ Viewport، SafeArea خام و تبدیل‌شده، Parent، مستطیل نهایی و حالت نمایش را ثبت کند. اندازه‌گیری پس از Layout انجام شود. برای مقایسه با اسکرین‌شات، مستطیل به مختصات فیزیکی صفحه تبدیل شود.

`print()` فقط خروجی کنسول/ADB است. اگر گزارش روی تصویر لازم است، Label/قاب تشخیصی جدا در DiagnosticsLayer با Mouse Filter برابر Ignore ساخته شود و در Release حذف شود. ابزار تشخیص نباید جای کنترل‌ها یا رفتار لمس را تغییر دهد.

برای نام نماها، [اصطلاح‌های صحنه](scene-view-terms.md)، برای سبک هنر، [راهنمای بصری](styleguide.md) و برای روش اتصال و تست APK، [راهنمای Android](android-wireless-debugging.md) مرجع هستند. قرارداد چیدمان همهٔ آن‌ها همین سند است.
